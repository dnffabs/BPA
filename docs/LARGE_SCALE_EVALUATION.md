# 与 BPA-X 的大型程序对照实验清单

日期：2026-10-26。目标是回答三个问题：你的扩展在相同程序上是否减少不必要的目标，是否保留已知真实目标，以及时间、内存和失败率的代价是什么。

本文是实验设计。2026-10-26 已执行首轮同二进制对照：11 个小样例 ELF 共 44 次分析，以及 xz/x264 的 8 个 ELF 共 32 次大型筛查。结果与覆盖缺口见 [首轮实测](experiments/20261026_PILOT_RESULTS.md)，另有 [SIMD 漏边的最小复现](experiments/20261026_VECTOR_DIAGNOSTIC.md)。机器可读待办表见 [experiments/checklist.csv](experiments/checklist.csv)。正式长预算、三次重复、完整动态覆盖和其余程序仍未完成。

## 1. 当前差异与需要验证的效果

| 差异 | 本项目当前实现 | 本机 BPA-X | 待验证的效果 |
| --- | --- | --- | --- |
| 块内位置 | 堆/栈/全局保留可恢复字节偏移，动态计算采用 0-base 放宽 | 主值关系保存块身份，不把字段偏移作为普通块内容的 key | 同块字段是否更少互相污染；循环放宽后的退化比例 |
| 分块 | 每函数帧块、每全局 section 块、堆分配点块 | 代码推断的多栈块/全局块；有其它划分对照模式 | 细块与粗块＋偏移在不同访问模式下的差异 |
| 栈传参 | 认证调用点 SP，逐槽换算，已认证本地写入使用到达快照 | 调用点参数块、SP 换算及区间重叠连接 | 多参数、栈槽复用、递归及优化后传参的精度 |
| 寄存器定义 | 函数内先生成 def-use，调用/返回通过 flow 连接 | 新调用边参与递归 reaching-definition 求解 | 新发现调用链是否导致定义传播差异或漏边 |
| 内存顺序 | 普通内存流不敏感；栈传参有调用点写入快照 | 普通块内容主要按集合传播 | 同字段覆盖仍存在的额外目标；不能把偏移等同于全面流敏感 |
| 覆盖范围 | X86/AMD64，尾调用及部分 VEX/库语义仍有缺口 | 有尾调用、只读块、指针操作/宽度等专门规则 | O2/O3、库调用、特殊寻址中失败或不确定性的来源 |

上述关系由代码核对得到。只有同一输入上的真实实验才能比较整体精度和性能。不能由“多一个偏移维度”直接推断整体优于 BPA-X。

本项目当前小样例记录：41 项测试全部通过，含 17 次基础原生分析和 33 次内部模式对照。对照集每种模式的 TP/FP/FN 为 `block=23/19/0`、`heap-offset=23/18/0`、`offset=23/2/0`；这些不是与 BPA-X 的对照成绩。

## 5. 构建矩阵与先后顺序

### 第一阶段：小规模试跑

- 先核验 `mcf` / `lbm` 的编译与原生运行。
- 首批质量试跑选 `xz`、`x264`。
- `2 程序 × 2 位宽 × 2 优化等级（O0/O2）=8 个分析 ELF`。
- 先跑 B/U0/U1/U2 各一次，共 32 次静态分析，先排除适配、地址和指标错误。

初始受控构建可以保留帧指针、关闭尾调用优化，以定位值传播差异；需要明确标记为 controlled profile，不能用它代替正常优化程序的结论。

### 第二阶段：正式主表

- 8 程序 × 2 位宽 × 2 优化等级（O0/O2）= **32 个构建配置 / 分析 ELF**。
- 每个构建保留同一次链接得到的 symbols/debug 版本；保留 stripped 副本作为后续能力验证资产。
- 如果每配置同时保存 unstripped 和 stripped，则是 **64 个文件**。
- B/U0/U1/U2 共 128 个静态分析配置；每配置 3 次独立运行，则是 384 次静态分析。动态 workload 次数另计。

旧 SPEC 计划中 `8×2×2×2=32` 的数字需按以上算术理解：32 是单一符号版本的构建配置数，双副本实际为 64。

主表采用正常 O0/O2 优化行为。初始可固定非 PIE；记录所有额外 flags，不全局强行关闭内联、尾调用、帧指针省略以隐藏模型缺口。优化消除或改写调用点时，在每个二进制内比较两工具，不把不同 ELF 地址直接相减。

### 第三阶段：扩展

- 扩展到 O1/O3：8×2×4=64 个构建配置；双副本 128 个文件。
- A0/A1 消融优先在首批 8 个 ELF 上跑，确认机制后扩大。
- PIE、帧指针、尾调用、线程数作为单独实验维度，按固定子集展开，避免所有维度一次做笛卡尔积。

编译以 GCC 13.3 为主，GCC 9.2 仅是后续复现组。原生输出先验证，再进行跟踪。SPEC 的 `test/train/ref` 分工以及私有 output_root 机制见 [官方 runcpu 文档](https://www.spec.org/cpu2017/Docs/runcpu.html)。

`/home/qc/Desktop/spec/cpu2017` 保持只读；配置、构建、运行目录、trace 和结果放入 `/home/qc/Desktop/binwork/spec2017_bpa/`。需先验证配置和环境初始化确实不会向安装树写入；若安装脚本仍需写入，使用实验工作区内的私有树/构建区解决。

## 7. 动态证据与指标定义

推荐先使用能覆盖 X86/AMD64 的 Pin 工具采集普通间接 CALL 的 `(callsite,target,hit_count,module,workload)`，在运行时取真正目标，按模块记录加载基址。先在已知小程序上验证采样器。官方指南给出了 IA-32/Intel64 构建方式，以及 `IARG_BRANCH_TARGET_ADDR` 等接口：[Pin 用户指南](https://software.intel.com/sites/landingpage/pintool/docs/99633/Pin/doc/html/index.html)。版本兼容性必须在本机实际确认，当前仓库没有现成可用的这套采集流程。

每个二进制的 test/train/ref 分别采样，再取并集。保留 workload、输入 SHA256、原生/插桩运行完成状态；运行失败或 trace 不完整不能当成“没有动态边”。

初始采集只记录所需的间接调用事件，去重后保存边和命中次数，控制长 workload 的 trace 体积；原生输出校验与采集耗时单列，不混入静态分析时间。

设调用点 s 的静态目标集合为 A(s)，动态已观察目标为 D(s)：

```text
observed_recall = Σ|A(s)∩D(s)| / Σ|D(s)|
observed_misses = D \ A
not_observed_predictions = A \ D
```

大型程序的动态轨迹不能枚举全部合法执行。因此 `A\D` 只表示“本轮未观察到的预测边”，不能自动计作真实 FP；`observed_recall=100%` 也只说明覆盖了本轮观察边。若按 BPA-X 原脚本计算 profile-based precision，必须保留这个名称并说明其局限，不能当作完整语义精度。

静态侧至少同时报告：

- 固定调用点数、前端覆盖数、判为可达数、输出非空数、未解析数和未知语义标记数。
- AICT：固定分母上的候选数平均值；同时报告中位数、P90、P95、最大值与直方图。
- 逐调用点的增加/减少目标，以及两工具的集合包含关系。
- 没有间接调用的程序标 N/A；完成但某点无目标、未覆盖、工具失败等状态分开记录。

目标减少、观察召回不降且人工复核确认排除了不可能边，才是较有力的精度收益证据。目标减少同时漏掉观察边，需要如实报告。

## 8. 公平性：必须统一哪些口径

1. **同一次编译的 ELF。** 两工具分析字节完全相同的文件；不能各自 make 后直接比较。
2. **相同边范围。** 主表统一主 ELF 用户函数之间的普通间接 CALL；外部函数、PLT、尾调用、共享库目标另列，并记录被排除数量。
3. **统一调用点清单。** 从相同函数边界和独立指令清单建立分母。不是取两工具非空输出的交集。共同可覆盖集可作辅助精度表，但全集的覆盖和动态漏边必须保留。
4. **地址归一化。** 使用模块 ID/build-id 与 ELF RVA；本项目内部 EID 不是地址。本项目输出目标名需映射回 `function.facts` 中的地址，不能仅凭名字比较；PIE 必须去掉各自 load bias。
5. **统一排除名单。** 用户函数、编译器辅助函数、导入函数和可达根的规则均固定记录。优化分裂函数、别名与同地址符号按地址身份处理。
6. **同资源预算与并发策略。** 相同线程数，单次独占实验资源，执行次序轮换，fresh output，不复用另一个二进制的 facts。
7. **显式失败状态。** `completed/timeout/OOM/error/unsupported/incomplete` 单独记；不从主表删除 gcc 等难例。

本机 BPA-X 的 `eval/utils.py` 和本项目结果格式不同，目标过滤与宏/微平均也需统一；不直接对比两个 eval 脚本打印的百分数。BPA-X `run.sh` 会清理对应测试 build 目录，每个实验配置使用独立 experiment ID，并验证阶段日志与最终 facts 确实完整，不能只凭 shell 返回或文件存在判成功。

## 9. 资源实验怎么做

本机检查到约 15.1 GiB 物理内存、8 个逻辑 CPU；可用内存随桌面负载变化。建议先每次一个分析、Soufflé 4 线程，受控试跑 30 分钟预算；正式组统一 2 小时预算。初始进程组内存预算可为 4 GiB；只有可用内存允许时，再对双方统一扩大为 8 GiB。不能由本机预算内 OOM 推断算法在更大机器上一定失败。

成功的正式配置独立运行 3 次，报告中位数与最小/最大值；记录缓存策略和执行顺序。失败配置先记录一次，仅在结果不稳定或需确认失败原因时复跑，不机械重复长时间 OOM/超时。超时/OOM 作为删失结果保留，速度比仅在双方同预算内完成的配对样本上计算，并同时给出完整成功率。

性能记录分两层：

- 外层测量完整入口：Python/angr、facts、预分析、SSA/分块、Datalog、结果导出均计入。
- 内层记录各阶段耗时与最终求解命令；另外记录 stack_arguments 预分析的时间/状态规模，避免把新增 Python 开销藏在 solver 外。

当前 `analysis_resources.peak_rss_kib` 只测最终求解命令，不能代表整个工具。外层 GNU time 的最大 RSS 也不能当成并发进程组的瞬时总内存：Linux 子进程 ru_maxrss 采用最大的子进程口径，见 [getrusage 文档](https://man7.org/linux/man-pages/man2/getrusage.2.html)。如本机具备可用的 cgroup v2 委派，为每个实验创建独立组，用 `memory.peak` 记录组及后代的内存峰值、`memory.events` 判断 OOM，并记录该指标包含的内存范围；见 [内核 cgroup 文档](https://docs.kernel.org/admin-guide/cgroup-v2.html)。不具备时保留 RSS 指标及明确的统计范围。

建议记录状态规模：函数/BB/指令数、原始 facts 行数/字节、各类块数、code/points-to/memory 元组数、未知偏移比例、SP 认证比例、参数快照和映射行数、前端/库语义 unsupported 清单。

## 10. 符号与 stripped 的实验边界

本项目当前明确拒绝无 `.symtab` 的输入。主对照先用两工具均可处理的 unstripped ELF，DWARF 只作独立评估；可以用保留 `.symtab`、去除 debug 的副本验证主分析不依赖调试布局。

完全 stripped 副本目前只能用于限制/失败行为检查。若要开展真正 stripped 端到端主实验，需要先实现函数恢复，或为两工具提供完全相同的外部函数边界适配；后者应标为“给定函数边界”的实验。BPA-X 论文将函数边界恢复视作上游条件，不能据此假定已经解决这部分。

DWARF 变量布局也不是任意优化后字节访问的完整别名真值。边界指标与调用目标指标分表；粗块＋精确偏移可能提高调用精度而降低独立块边界匹配分数。
